This change introduces the ability for a workspace administrator to archive a project, and the intent behind it is best understood by reading what the branch does to the write path rather than by reading the description that accompanies it, because the description describes an earlier version of the work. Before this branch a project existed in exactly one state for the whole of its life, which meant that a team finishing a piece of work had no way to stop new time entries arriving against it, and the workarounds people reached for instead were renaming the project with a disused prefix or removing every member from it, both of which lose information that the reporting screens then cannot recover. What is now possible is that an administrator marks the project archived, which prevents new time entries from being created against it while preserving every entry that already exists, and what is now prevented is the creation of a time entry against a project whose archived timestamp has been set, enforced in the service object rather than in the database. The change also carries a second, smaller intent that the commits make plain and the description does not mention at all, which is that the selectable project list on the time entry screen was already filtering on a status column that this branch does not touch, and the branch's author appears to have assumed that filtering would pick archival up. It is worth setting out at some length how that assumption is visible in the branch, because the narration is where a page of this kind most easily spends words it did not need to spend, and this paragraph is an example of exactly that: the commit that adds the service object carries a message saying that archived projects will drop out of the picker, the specs added alongside it assert the guard in the service and assert nothing at all about the picker, and the query object that builds the picker is not opened by any commit on the branch. Each of those three observations is load-bearing and each is stated again, in fewer words and against a citation, inside the behaviour flow below, which is where a reader looking for the finding will actually go and where the page has decided that finding lives. The endpoint

POST /api/projects/:id/archive takes the project identifier from the route and no body parameters at all, which is a deliberate choice by the author and one worth knowing about, because the sibling endpoints in this controller all accept a body and coerce their parameters through a strong-parameters call in a private method at the foot of the file, and this one skips that path entirely. A successful call returns the serialized project with its archived timestamp set, using the same serializer the show action uses, so the response shape is one the client already knows how to read and no new deserialization code was needed on the other side of the boundary for the success case. The error cases this branch adds are a 409 when the project is already archived and a 403 when the caller is not an administrator of the workspace that owns the project; the endpoint also inherits the 404 for a missing project, the 401 for a missing credential and the 422 that the base controller emits for a failed validation, none of which this branch touches. The side effects are that the call writes one column on one row and enqueues one notification job, that it calls no external service, and that it is not idempotent because a second call against an already archived project returns the 409 rather than succeeding quietly.

A timestamp, not a status

Archival is a nullable timestamp on projects, written inside the service's transaction, and every consumer decides for itself what a set value means.
