Admins can resize report cards on the admin dashboard, and the size is saved

Each report card gets a corner handle. Dragging it sets a width of one or two columns and a height of one to four rows. A card taller than one row always takes the full width. A plain click switches a card between its normal size and full width. The size is saved in two new columns on admin_dashboard_reports and sent back with the dashboard section.

What changed

A report card's size is now part of the saved dashboard layout

Before this change, the reports layout was an ordered list of reports. Every card was the same size. Now each entry also has rows (1–4) and cols (1–2), and a card taller than one row must span both columns. The layout endpoint still replaces the whole list on every save. As a result, any request that leaves out a card's size now resets that card to one cell. Only admins see the handle, and only after the card's data has loaded. The handle is hidden on narrow viewports. The commits also add reduced-motion handling and right-to-left handle placement. The description says cards “remember their size”. Checkpoint A tests that claim against the one writer the diff did not touch.

Checkpoint A

Checkpoint B

Is this.cards a safe source for the sizes the next PUT sends?

layoutItems used to map @data.items, the server's copy. It now maps this.cards, at frontend/discourse/admin/components/dashboard/reports.gjs:162-169. setSize updates this.cards only after its PUT resolves, and it never refreshes @data. Two consequences follow. If a second resize starts before the first PUT returns, it sends the first card's old size inferred. And loadPayloads rebuilds the cards from @data.items. After a date change that data is refetched and correct, but when the dashboard re-serves its cached copy it still holds the sizes from before the resize. Decide whether local state can safely stand in for the server's copy on both paths.

  • The PUT built before the await nextItems reads this.layoutItems, and this.cards is only reassigned on success frontend/discourse/admin/components/dashboard/reports.gjs:389-409

Checkpoint C

Which layer actually enforces “a multi-row card is full width”?

The rule is written three times: in the controller at app/controllers/admin/dashboard_controller.rb:244-246, in model validations at app/models/admin_dashboard_report.rb:40-43, and in the client's clamps. The only production write goes through insert_all, which never instantiates a model and so runs no validations, and the table has no CHECK. So the model validations run only in seeds and specs, and the controller's parser is the real guard. That parser is also shared with the bulk-fetch endpoint. Decide whether that is enough, given that computeColumns ignores rows and relies on the rule inferred.

Checkpoint D

Should a plain click on a tall card's handle collapse it to one cell?

A press that never passes the 8 px threshold counts as a click. A 1×1 card goes to full width. Every other size, including a four-row card, goes straight to 1×1 and is saved. The handle's own contract says to commit only when moved is set from unchanged code. This component commits on a click on purpose. Decide whether collapsing a tall card on an accidental click is the intended behaviour. On narrow viewports the handles are hidden but --rows-N still spans rows, so a phone shows a tall card that cannot be shrunk there.
