What changed

Admins can resize report cards, and each card keeps its size

The redesigned admin dashboard shows the reports an admin has pinned as a grid of cards, two columns wide. Admins already choose which reports appear and in what order. Every card was the same size, though, one fixed-height cell, so a report with more to show had to fit in it.

Each pinned report now carries a stored size: one to four rows tall and one or two columns wide. Two new columns on the dashboard's layout table hold it, and both default to 1. The layout endpoint accepts a size with each report, and it rejects a size out of range, or a card taller than one row that does not span both columns. The dashboard returns each card's size alongside its other fields. In the browser, an admin drags a card's lower corner to grow or shrink it, watches it reflow live, and the size is saved on release. A click on the corner without dragging toggles the card's width instead. The handles appear only for admins, and not while a card is still loading.

Admins get layouts that survive a reload, and anyone else who can open the dashboard sees the sizes admins chose. A dashboard where no card has been resized looks as it did: every existing row reads one row by one column, which is how every card rendered before.

Checkpoint A

Saving the report list from the Manage reports modal

The dashboard now has two ways to change its list of pinned reports. The gear on the reports section opens a Manage reports modal, where an admin adds, removes and reorders reports and then saves. The cards themselves offer the second way: the corner handle that sets a card's size. Both save through the same layout endpoint, and that endpoint stores whatever list it receives as the complete layout, replacing every row it held before.

So a card's size survives a save only if that save sends it. The resize handler sends every card with its current size. The modal, which this change does not touch, still sends each report's source and identifier and nothing else:

The endpoint treats a missing size as the smallest one: an absent row count or column span becomes 1, and the layout is then deleted and re-inserted from the list as received. After any save from the modal, even one that only reorders two reports, every card on the dashboard is back to one row by one column from unchanged code.

The modal does hold the sizes. It loads its enabled reports from the same section builder the dashboard uses, which now returns each report's size; its save maps them away. The path is drawn in Impact outside the diff.

Checkpoint B

Saving one card's size by rewriting the whole layout

The dashboard stores its pinned reports as one list, and the only way to change any part of it is to send the whole list again: the layout endpoint deletes every stored row and inserts the list it was given. Removing a report from the dashboard already worked this way.

Resizing now works this way too, and an admin does it far more often. When a resize ends, the handler builds the full list from the cards this browser holds, with the new size swapped in for one card, and sends it. When the request succeeds it updates its own copy of the cards, without reloading the dashboard. The list sent is a snapshot of this browser's view, so anything missing from that view is missing from the stored layout afterwards.

Two things can be missing from it. The first is another resize still in flight. Each save builds its list from the cards as they stood when it began, and a card only takes its new size once its own request returns. Two overlapping saves, such as clicks on two cards' handles in quick succession, would each send a list without the other's change. The one the server handles last wins, while the browser shows both sizes inferred. The test that a second resize carries the first one's size runs them one after the other.

The second is a stored report the dashboard never shows. The section shows only reports whose source still has a registered provider and, of those, the ten most recently created. A row whose source has no provider is dropped by the provider lookup from unchanged code, never reaches the browser, and is deleted by the next resize. Removing a report or saving the modal already did this; resizing adds a trigger that fires much more often.

Checkpoint C

Where the card-size rules are enforced

A card's size has three rules: one to four rows, one or two columns, and a card more than one row tall must span both columns. The last rule keeps the grid free of gaps that the browser's own placement arithmetic does not expect inferred. The change writes these rules down three times.

The browser does not produce a size that breaks them: while dragging, it clamps the row count and switches a card to full width as soon as it is taller than one row. The layout endpoint checks them again before saving and rejects the whole request if any item fails. And the model gains matching validations, including one for the full-width rule.

The model's validations do not run when the layout is saved. The endpoint hands its list to the layout updater, which writes it with a bulk insert, and insert_all builds no model objects, so no validation runs on that write. The model's rules are reached only by the seeders that create the default reports, which never pass a size from unchanged code. The database adds a default of 1 and a not-null constraint, and no check. In practice the endpoint's check is the one in force.

The same check also guards a request that only reads. Each card's chart data is fetched through a bulk endpoint that parses its items with the same method, and the browser now sends each card's size with that request. A stored size the check refuses would fail the request, and the dashboard then marks every card as errored, not just the one. Neither the endpoint nor the default-report seeders, the only other writers, can store such a size from unchanged code; a later writer that skips the endpoint could.

Checkpoint D

What a click on a resize handle does

The corner handle does two jobs. Dragged, it sets any size the rules allow, a row or a column at a time. Pressed and released without moving, it reports a gesture that never moved, and the handler treats that as a shortcut:

frontend/discourse/admin/components/dashboard/reports.gjs:361-368 At head

    if (!dragInfo.moved) {
      this.liveResize = null;
      const isNormal = item.rows === 1 && item.cols === 1;
      await this.setSize(
        item,
        isNormal ? { rows: 1, cols: MAX_COLS } : { rows: 1, cols: 1 }
      );
      return;

A card at the smallest size becomes one row at full width. Every other size, including a card two, three or four rows tall, goes straight back to the smallest. The shortcut is a toggle between two sizes over a range of eight, and the result is saved at once. An admin who presses a tall card's corner meaning to start a drag, and lets go, loses the height and has to drag it back. A press only becomes a drag after eight pixels of travel, so a short, hesitant drag counts as a click too.

Checkpoint E

Animation and pointer-following written inside the dashboard component

Two pieces of the resize experience have nothing to do with reports. One animates the other cards sliding into their new grid positions as a card grows; the other pins the dragged card to a rectangle that follows the pointer. The change writes both as modifier classes at the top of the dashboard component: a layout-change animation and a modifier that places an element at a given rectangle. Both take an element and plain values, with no reference to reports.

The repository's agent guide says UI is built from the ui-kit primitives rather than hand-rolled behaviour, and that new shared, domain-free primitives go there from unchanged code. The ui-kit's modifiers directory holds twenty, among them drag, pointer-drag and resize-observer modifiers, and none animates a layout change or places an element at a rectangle from unchanged code. So nothing existing was bypassed; what is open is where these two new ones belong.
