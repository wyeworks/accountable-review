What changed

Every confirmed gem ownership now leaves a durable record of who held it

A new historical_ownerships table records that a user once held a gem, at what highest role, and between which two moments. Four callbacks on Ownership keep it in step with the live table: one opens a row when an ownership is created already-confirmed or is later accepted, one ratchets that row's role upward on promotion and ignores demotions, and one stamps removed_at on destroy. Rubygem#disown deletes ownerships without running callbacks, so it closes its rows explicitly. A maintenance task backfills one open row per currently-confirmed ownership.

Nothing reads the new table yet — the description says this is the first of three slices of #6534, and that the backfill has to finish before the other two are merge-safe. The partial unique index on (rubygem_id, user_id) WHERE removed_at IS NULL is what every write path here depends on.

Attention

What needs your attention

Five judgments. The first four turn on whether the new table stays true to the live ownerships table under paths this PR did not touch; the last is about where the role ordering belongs. The order is the order to think about them.

Checkpoint A

Should moving a gem into an organization end its owners' recorded tenure?

close_historical_ownership stamps removed_at on every Ownership destroy, with no test of who is destroying it. Both organization paths destroy exactly the ownerships of the users who are joining the organization, after the Membership rows are created and the gem has taken its organization_id — because access now comes from the organization from unchanged code. Each of those users is therefore recorded as having stopped owning the gem at the moment of transfer, so HistoricalOwnership.current omits people who still have access and .alumni claims people who never left.

Checkpoint B

Is the backfill safe to run while the application is writing?

doc/maintenance-tasks.md asks a task that races the application to preserve newer writes and to skip records deleted after collection from unchanged code. process writes role and first_owned_at from the record its batch materialised, so a promotion landing after that load is written back at the old role — the ratchet callback ran first, against a row that did not exist yet, and matched nothing. An ownership destroyed after that load is the sharper case: its own close_historical_ownership found nothing open, and process then creates a row that nothing will ever close inferred.

Checkpoint C

Is one row per tenure the grain the next two slices need?

The unique index constrains only the open row, so closed rows accumulate freely: a user who owns a gem, is removed, and owns it again ends with two, and the second row's first_owned_at holds the start of the second tenure rather than the first. current and alumni therefore answer “is this tenure open”, not “has this user ever owned this gem”, which needs a distinct across both. The role ratchet is per tenure too, so a user who was an owner, left, and returned as a maintainer reads as a maintainer.

Checkpoint D

Should a failed history write roll back the ownership change itself?

All four hooks are after_create, after_update and after_destroy, so they run inside the Ownership save transaction, beside the existing event recorders that already work that way from unchanged code. The new model carries no validations, so role and first_owned_at being NOT NULL, and one open row per pair, are enforced by Postgres alone: a violation raises out of the callback and takes down the confirmation or the removal the user asked for. close_historical_ownership is deliberately tolerant of finding nothing; the two creating paths are tolerant of nothing.

Checkpoint E

Should the role ordering live in Access rather than on the model?

lib/access.rb already owns the ordering: ROLES carries the flags and with_minimum_role turns a role into the range above it, which is how both Ownership and Membership ask their version of this question from unchanged code. This PR adds a second ordering beside it — ROLE_HIERARCHY, derived from the enum at class-definition time, and roles_below, returning role names — so “at or above” is a range of integers in one file and “below” is an array of strings in another. Both are correct today.
