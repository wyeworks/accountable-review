What changed

Ending an ownership now leaves a history row behind

rubygems.org starts recording who has ever owned or maintained a gem. The new historical_ownerships table holds one row per stint: Ownership callbacks open a row when an ownership is confirmed (an invitation counts only once accepted), raise its role on promotion but never lower it, and stamp removed_at when the ownership is destroyed. Rubygem#disown, which deletes ownerships without callbacks, closes the rows itself. A maintenance task opens rows for every ownership confirmed today; the description says stints that ended before deploy are deliberately not reconstructed, and that this backfill must finish before the two follow-up PRs are safe to merge. No code in this PR reads the table; the description says the follow-ups will.

What needs your attention

Four judgments, all about whether the history table stays true to the ownerships it mirrors. The order is the order to think about them.

Checkpoint A

Does every path that starts or ends an ownership keep exactly one open history row?

The history follows ownerships only through writes that run Ownership's callbacks. Every destroy caller runs them, including account deletion at app/models/user.rb:376 and the organization flows (app/models/organization_onboarding.rb:130) from unchanged code, and disown skips them but closes the rows itself. script/merge_users (script/merge_users:44-51) does neither: changing ownership.user touches no column a history callback watches, so the open row stays on the discarded account and is deleted with it, leaving the kept account with a confirmed ownership and no open row from unchanged code. Decide whether that path, and any future write that re-points an ownership, needs its own handling.

Checkpoint B

When members' gems move into an organization, should their history rows close?

Onboarding and gem transfer destroy the direct ownerships of members who join (app/models/organization_onboarding.rb:126-130), so each destroy now stamps removed_at on that member's row from unchanged code. Those members keep access through the organization, so the table will record them as former owners of gems they still publish. The description says later slices will show prior owners on gem pages; decide whether removed_at means the Ownership row went or the access did, because the follow-ups will read it as one of the two. Checkpoint C

Can the backfill open a history row for an ownership that is already gone?

process creates from the ownership the task loaded, without reloading it. If that ownership is destroyed after its batch loads, the destroy callback finds no row to close and the task then opens one for a user who no longer owns the gem, which the partial unique index cannot refuse because no other open row exists inferred. This repository's maintenance-task guide asks tasks to handle that case (doc/maintenance-tasks.md:9-11) from unchanged code. Removals that land before the task reaches an ownership leave no trace at all, and backfilled rows carry today's role rather than the highest held. Decide whether that window matters before the follow-up PRs rely on the data.

Checkpoint D

Should history rows be destroyed with their user?

User and Rubygem now declare has_many :historical_ownerships with dependent: :destroy. Account deletion is a soft discard that destroys ownerships but leaves the user row, so the ordinary path keeps the history. A hard destroy deletes it; the one found is script/merge_users:51, which erases the merged account's rows from unchanged code. Destroying a Rubygem would delete its rows the same way (app/models/rubygem.rb:15). Decide whether rows in a history table are meant to disappear with the account or gem they describe.
