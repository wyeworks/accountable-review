Email-code signup asks for a username before the account exists

A correct code no longer creates a new member's account by itself. The server answers with a details step, and the account is created by the request that brings the chosen username back.

What changed

The account is created by the request that carries the username

For a new address on an open site, a correct code now returns username_required with a suggested name. The form shows a details step for username and avatar, and a second verify request carrying the chosen name creates the account. CAPTCHA, username validation and consuming the code all move to that second request. An avatar picked on the step is saved by the browser once the account exists. A plugin can also switch the step to a server-generated name that the form submits by itself. The description says this restores a reverted change with a distinct details state.

Two smaller changes ride along:

  • A caller checking a username for another user (for_user_id) must now be signed in and allowed to edit that user's username.
  • enable_random_usernames now defaults to off.
Before
Entering the code created the account with a generated name, which the new member could then rename.
After
The new member chooses the name, and optionally an avatar, before the account is created.

Checkpoint A

Does every request that creates an email-code account still pass CAPTCHA?

The patch used to demand a token on the request that submitted the code. It now demands one only when the request carries a username, is not an approval signup, and has no user fields or full name missing. Those negations mirror the controller's early returns, so the requests it lets through stop at required_username_provided before the code is consumed. Approval signups are checked on the completion request instead. Decide whether that mirroring holds for every way a request reaches EmailLoginCode::Redeem.

Checkpoint C

What should the server-side generated-username flag change?

The controller sets generated_username only when a proof in the server session matches the code, the email, the name and the signup context, and Redeem forwards it to CreateFromVerifiedEmail, whose call never reads it. Its whole server-side effect is in the controller: a rejected generated name is replaced with a fresh one instead of returning an error. The mode is only on when a plugin registers email_login_code_username_mode; otherwise lib/discourse_plugin_registry.rb:306-310 returns the default, and no plugin in this repository registers it from unchanged code. The same is true one layer up: the contract still declares username_required at app/services/email_login_code/redeem.rb:11 and the approval completion still sends it at app/controllers/session_controller.rb:1095, but no policy reads it any more. Decide whether each unused input is leftover plumbing or a missing behaviour.

Checkpoint D

Is it acceptable that a chosen avatar can be lost without a word?

The avatar is picked before the account exists and saved by the browser after account_created: an upload then pickAvatar, or selectAvatar for a preset, with every failure swallowed before the redirect. The picker offers upload when can_upload_avatar is true, which only checks groups, but the upload endpoint also refuses avatars when auth_overrides_avatar or discourse_connect_overrides_avatar is set (app/controllers/uploads_controller.rb:51-56) from unchanged code. On such a site a member can choose a file, see it previewed, and arrive with the default avatar. Approval signups never reach this save, because app/controllers/session_controller.rb:1180-1181 answers pending_approval first.

Checkpoint E

Should sites that never set enable_random_usernames lose random names?

The setting arrived on 2026-08-27 defaulting to on, and this flips the default. Every site still on the default stops getting adjective-and-noun suggestions on the username and approval details steps, loses the regenerate button (frontend/discourse/app/components/code-login-form.gjs:1282), and gets a 404 from the random-username endpoint. The plugin-driven generated mode ignores the setting through allow_when_disabled: true. Whether a release shipped with the old default is uncertain; the release tags would settle it.

Checkpoint F

Does the new for_user_id guard turn away a caller that still needs it?

check_username used to load any for_user_id for any caller, anonymous included, and check availability against that user's email. It now raises for an anonymous caller and requires ensure_can_edit_username!; the signup form stopped sending the id. The username preference, which does send it, only shows its edit control when the serialized can_edit_username is true, computed by the same guardian method at app/serializers/user_serializer.rb:216-218 from unchanged code.
