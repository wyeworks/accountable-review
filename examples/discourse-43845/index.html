Email-code signup picks a username before the account exists

The first correct code no longer creates an account. It is verified and left unconsumed, and the account is created by the next request, which carries the code and the username the person chose.

What changed

The account is created by the request that carries the chosen username

Before this change, the first correct email code created the account under a suggested or random name, and a follow-up step let the new person rename it. Now that request verifies the code without consuming it and answers username_required. The account is created on the next request, which carries the code and the chosen name, and the CAPTCHA check moves with it. The avatar is picked on the same step and uploaded once the account exists. Email-code invitations follow the same rule. A plugin can also ask the server to generate the username itself, through a new modifier that no code in this repository registers. The description calls this a server-controlled flow that uses “the normal validation and CAPTCHA checks”. Separately, check_username now refuses for_user_id to anyone who cannot edit that user’s username.

  • A new person signing up by email code chooses a username before the account is created.
  • Every site still on the default loses random adjective-noun usernames, because enable_random_usernames now defaults to false.
Before
A correct code created the account straight away; the username and avatar were edited afterwards, on an already-created account.
After
A correct code opens a details step; the account exists only once a username is submitted with the code, and a chosen avatar is uploaded after that.

Each question below turns on which request now creates the account and what that request trusts. They are ordered by what would cost most to misread. The last one is about where the new code was put.

Checkpoint A

Does every request that can now create an email-code account still pass CAPTCHA?

The CAPTCHA plugin now asks for a CAPTCHA only when the request carries a username and is not an approval signup. That is meant to track account creation: EmailLoginCode::Redeem will not create an account without a username, and a request missing required fields or a full name is answered before Redeem runs (app/controllers/session_controller.rb:972-976). On approval sites the first step no longer checks CAPTCHA, so the completion gate is the only check. Decide whether a username is present is an exact stand-in for this request can create an account: a creating request the gate skips is the gap to look for.

Checkpoint B

Is the generated_username flag meant to change anything once it reaches account creation?

When a plugin’s email_login_code_username_mode modifier answers :generated, the server picks the name, stores a proof keyed by the login code, and passes generated_username through EmailLoginCode::Redeem into CreateFromVerifiedEmail. That action declares the option and never reads it, and switches username restrictions on from username.present? alone. The flag’s only effect is in the controller: a generated name that fails is answered with a fresh candidate instead of an error (app/controllers/session_controller.rb:1004-1013). No code in this repository registers the modifier, so here the path runs only in specs. Decide whether the option is leftover plumbing from the commit titled “Support trusted generated usernames” or a missing behaviour.

Checkpoint C

Is the login code’s ten-minute life enough for the new details step?

The code now has to last through the whole details step — username, avatar, CAPTCHA — because it is consumed only when the account is created. It still expires ten minutes after it was sent, and the generated-name proof expires with it (app/controllers/session_controller.rb:1379-1380). A lapsed code returns the generic invalid-code error on a step with no way to request a new one: the change-email button exists only on the code step (frontend/discourse/app/components/code-login-form.gjs:1246-1252) from unchanged code. Each retry also counts against the verify rate limit (app/controllers/session_controller.rb:15-16). Decide whether ten minutes and that dead end are the intended bounds. Impact path B draws the consequence.

Checkpoint F

Is it acceptable that a chosen avatar can silently fail to save?

The avatar is now chosen before the account exists and uploaded by the browser afterwards, and any failure there is swallowed so the redirect goes ahead. Two cases lose a chosen file with no message. The upload option is offered from a prediction — default trust-level groups plus any invite groups (app/controllers/session_controller.rb:1317-1332) — while the upload is gated on the created account’s actual groups. And UploadsController refuses avatar uploads when an auth provider owns avatars, a setting neither check reads from unchanged code. The first commit says upload failures should not interrupt signup; decide whether failing silently is the intended form of that.

Checkpoint G

Is it deliberate that the new signup logic lives in SessionController rather than a service?

The PR adds about a hundred lines of signup policy to SessionController: choosing and validating generated names, storing and matching the proof, and predicting avatar permission. The project’s guide says business logic — validation, models, permissions — is extracted from controllers into services, and the signup policies themselves already live in EmailLoginCode::Redeem. The approval continuation, which came first, also keeps its proof in this controller (app/controllers/session_controller.rb:1054-1075). Is putting the new helpers here deliberate?

  • The written convention extract validation, models and permissions from controllers CLAUDE.md:63-64
  • The service that holds the policies every signup policy, including the new username one app/services/email_login_code/redeem.rb:39-49
  • The new controller helpers from render_signup_username_required to complete_login_code_authentication app/controllers/session_controller.rb:1299-1406
