FIX: Separate email-code signup details from completion

Email-code signup stops creating the account on code verification. The person picks a username first, and the account is created on that submission, along with the CAPTCHA check and the chosen avatar.

What changed

Email-code signups now ask for a username before the account exists

Before this change, verifying an email code created the account straight away with a generated username, and the person could rename it afterwards on an "account ready" step. Now the verify endpoint answers username_required with a suggested name. The account is created only by a second submission that carries a username, for open signups and for invite redemptions alike. A rejected name comes back as a field error and the code stays unspent. The avatar picked on that step is uploaded once the account exists. CAPTCHA is checked on the submission that creates the account, and random usernames are now off by default. The description says this restores an earlier change that was reverted, now with a separate details state.

  • A new visitor or an invitee chooses a username before their account is created, and CAPTCHA, the avatar and the random-username default move with that step.
  • A plugin can switch a signup into a "generated username" mode. The server picks the name and remembers it for that login code, and the client submits it without asking.
Before
Code verified, then the account was created with a generated name, then an optional rename on the "account ready" step.
After
Code verified, then a username is chosen, then the account is created and the chosen avatar applied.

Checkpoint C

What does "generated" mode actually trust, when nothing in core turns it on?

A modifier chooses the mode, core never registers it, and so every core site runs :required. When a plugin chooses generated mode, the server stores its pick in server_session. It accepts that name back only if the login code, email, username and signup context all match. The resulting flag reaches CreateFromVerifiedEmail and is never read there, so a generated name goes through the same model validation as a typed one. Its only effect is in the controller, where a rejected generated name gets replaced instead of returning an error. You need to decide whether that unread option is unfinished work or room left on purpose.

Checkpoint D

Should sites already running code signup lose random usernames on deploy?

enable_random_usernames came in with 1df32987f9 on 27 August with a default of true. This PR changes the default to false, and no migration keeps the old value for sites that never set it. Checkpoint E

Is it acceptable that a chosen avatar can be dropped silently after the account exists?

The avatar is no longer saved when it is picked. The browser holds it and applies it after the account is created, and any failure is swallowed so signup still completes. The commit message says the swallow is intended. The upload option on the details step is a guess made before the user exists. It uses the default trust-level groups, plus everyone unless granular group permissions are on, plus the invite's groups. After creation, the check uses the user's real groups and gates only file uploads. Where the guess and the real check disagree, the picked file is skipped and nothing is shown. You need to decide whether quietly keeping the letter avatar is the outcome you want.
