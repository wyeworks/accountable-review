What changed

Email-code signup asks for a username before the account exists

Email-code signup lets someone join with only their email address: the site mails a code, and entering it proves the inbox is theirs. Until this branch, entering the code created the account straight away, with a name suggested from the email or made up from a word list, logged the person in, and only then offered a step to rename the account and pick an avatar.

  • A new person signing up with an email code now chooses a username after the code is checked and before the account exists. The browser sends the same code a second time with the name, and the code is used up only then. CAPTCHA, the avatar choice and a plugin-selectable mode in which the server picks the name all move to that second request.
  • Asking whether a username is free on behalf of another account now requires being logged in and being allowed to rename that account.

The account is no longer created until a name has been chosen and accepted. Alongside it, random usernames are now off by default, so the username field starts empty unless the email suggests a name. The description presents the branch as restoring username-before-creation signup after an earlier version was reverted.

Before
Entering the code creates the account with a generated name and logs the person in; renaming it is an optional step afterwards.
After
Entering the code asks for a username; the account is created and logged in only when that name is submitted and accepted.

Attention

What needs your attention

Four judgments about the new signup sequence — when the code expires, where CAPTCHA is checked, what a server-picked name changes, and what happens to an avatar picked early — then one about the username check. The order is the order to think about them.

Checkpoint A

Creating the account only once a username is chosen

The first request a new person sends with their code used to create the account. It now stops short of that. EmailLoginCode::Redeem runs its policies before it opens the transaction that uses up the code and creates the user, and the username policy, now the last of them, fails when no name was sent. The controller answers that failure with username_required, a suggested name and avatar details, and the browser shows a details step. Continue sends the same code again, this time with the name, and only that request uses the code up.

The second request is where the timing matters. Sending a code twice does not exhaust it: verify spends an attempt and gives it back when the code matches from unchanged code. But nothing extends the code's life. A code is valid for ten minutes from when it was mailed from unchanged code, and those ten minutes now have to cover reading the email, entering the code and choosing a name. Every Continue is also one more request against the verify limit of six a minute and thirty an hour per IP.

When the code has expired by the time the name is submitted, the request fails like any wrong code: the controller renders the generic invalid-code error, and the form shows it on the details step. That step has the username field, the avatar button and Continue. The control that goes back to request a new code exists only on the code step. The signup page around the form adds nothing on that step: it renders the form, plus a disclaimer on the email step only. Reloading the page would start again from the email step inferred.

GAPNothing tests a code that expires while the person is still choosing a name.

Checkpoint B

CAPTCHA on the request that creates the account

CAPTCHA for email-code signup lives in a plugin, discourse-captcha, which wraps SessionController methods: before the core verify logic runs, it decides whether this request needs a solved CAPTCHA and rejects it when the token is missing or wrong. Sites that approve each new account by hand finish signup on a separate request, and the plugin checks CAPTCHA there unless the earlier request already did.

The plugin used to demand CAPTCHA on the code request because that request created the account. It now demands it only when the request carries a username, the person is not heading for approval, and the required fields and full name are present. The browser moves with it, running the CAPTCHA step on the details Continue and on the approval details submit. Three requests can create an email-code account, and every one that is not an invitation has to end up behind a CAPTCHA:

The requests the new condition lets through without CAPTCHA are ones that create nothing. A request with no username fails the username policy before any write. A request missing required fields or the full name is answered with a request for them before the service runs. The mode in which the server picks the name would send the second request on its own, and the plugin switches that automatic submit off so the person can solve the CAPTCHA first. One cost remains: the browser posts the token to the plugin before the request, so a submit that comes back asking for fields, or carrying a name that is only spaces, has used up a CAPTCHA no account consumed inferred.

Checkpoint C

Usernames the server picks when a plugin asks it to

The branch adds a second way through the details step, for sites where a plugin decides people should not choose a name at all. The controller asks the email_login_code_username_mode modifier, a hook a plugin registers to override a value core computes. It defaults to :required, and the only code in this repository that registers it is two request specs, spec/requests/session_controller_spec.rb and the CAPTCHA plugin's session_controller_spec.rb from unchanged code. When it answers :generated, the server picks a name: the email's suggestion first, then up to four random ones, each checked for format, route clashes and availability, and the availability check also refuses reserved names from unchanged code. It records the name in the server-side session against the code, and the browser submits it at once without showing the field.

A browser cannot claim this mode for a name it chose itself. The second request counts as generated only when the stored record matches the code, the email, the name and the signup context, and the modifier still answers :generated. What the flag changes after that is narrow. When the name is reserved or the user model rejects it, the controller answers with a fresh candidate rather than an error, and the browser retries twice at most before showing the field. The flag is also passed into the service that creates the user, which declares it:

app/services/user/action/create_from_verified_email.rb:3-6 At head

class User::Action::CreateFromVerifiedEmail < Service::ActionBase
  option :email
  option :username
  option :generated_username, default: -> { false }

Nothing in that service reads the option, and username restrictions are enforced whenever a name is present, so a server-picked name is validated exactly like a typed one. That matches the description's "uses the normal validation". Random names in this mode also ignore the setting that now turns random names off by default.

Checkpoint D

Keeping an avatar picked before the account exists

The old details step ran after login, so the avatar picker worked on a real account. Now there is no account yet, so the picker opens in a deferred mode: it remembers a chosen file or a site-provided avatar and saves nothing. Once the account exists, the form uploads the file, assigns it and then redirects.

Whether to offer an upload at all is decided before the account exists. The controller estimates it from the groups the new account is expected to join: the default trust level's groups, or the invitee level's, plus logged-in users and any invitation groups. After creation the form uploads only when the creation response, which checks the account's real membership, says uploads are allowed, so a file picked under an estimate the account does not match is dropped in the browser, with no request sent. The upload endpoint can also refuse for a reason neither check looks at: it refuses every avatar upload while an auth provider or DiscourseConnect overrides avatars from unchanged code, and the form catches and ignores that failure so signup still finishes. Either way, the picked file is dropped without a word, and the person ends up with the letter avatar inferred.

The silence is deliberate: the comment on that catch says avatar customisation must not block an account that was created. How often the estimate and the real membership differ on a real site was not established uncertain, because membership at creation is decided by group automation outside this change.

Checkpoint E

Checking a username on behalf of another account

The username availability endpoint accepts an optional for_user_id: the account whose name is being changed, so that its email and current name count when deciding whether a name is free. Before this branch it loaded that user for any caller, anonymous ones included. It now requires a logged-in caller who is allowed to rename that user, and refuses everyone else with a 403.

The signup form no longer sends the parameter, and the validation helper behind the other signup forms passes only a name and an email from unchanged code. The one remaining caller that sends it is the username field in account preferences, which sends the profile's user id from unchanged code. That field is shown only when can_edit_username is true, and that value comes from the same Guardian check the endpoint now enforces from unchanged code, so it keeps getting answers. Callers outside this repository, such as API clients, are beyond what a search here can see uncertain. Available names now also come back with the default avatar for that name, which the signup form previews.
