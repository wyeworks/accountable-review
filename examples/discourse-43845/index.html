Email-code signup waits for a username before it creates the account

The verify endpoint now answers a code with a request for a username instead of a finished account, and everything that used to run after account creation — the username check, the avatar picker, the CAPTCHA gate — moves ahead of it.

What changed

The account is created last

An email-code signup used to create the account the moment the code verified, stamp a server-generated username on it, and then offer an “account ready” step where the user could rename it and pick an avatar against the account that already existed. Now the first verify response asks for a username; nothing is written until a second request carries one. Four consequences travel with that reordering: invite redemption takes a username too, the CAPTCHA gate moves to the request that creates the account, check_username stops accepting an arbitrary for_user_id, and enable_random_usernames flips to off by default now that the user picks. The description frames this as restoring a reverted change with a distinct details state.

Before
The code verified, the account existed, and its username was a placeholder the user was invited to replace afterwards — by which point a failed rename left a real account named user7.
After
The code verifies, the server asks for a username, and no row is written until one is accepted; the avatar chosen on that step is held in the browser and applied once the account exists.
Attention

What needs your attention

Every one of these follows from the same reordering — the account is now created by the second request rather than the first — and they are in the order worth thinking about them in, starting with the gate that does the reordering.

Checkpoint A

Is a username now required on every path that creates an account, and what does a rejected one cost?

The policy that demands a username used to read !params.username_required || params.username.present? — enforced only when the client asked for it — and is now unconditional for a new account. With CreateFromVerifiedEmail's three-way fallback deleted, nothing can invent one any more. What is left to decide is the cost of a refusal, and the two refusals are not alike: a policy rejects before the transaction opens, while a name the model refuses fails inside it — after consume_code has already spent the login code. from unchanged code

Understanding Ruby on Rails ActiveRecord::Base.transaction
A raised exception is what rolls a transaction back

A Rails transaction is not undone by a method returning false. It is undone by an exception escaping the block: the adapter issues ROLLBACK as the exception unwinds, and then re-raises it. Code that merely returns a falsy value inside the block commits everything written before it.

That is why the safety of a two-request signup rests on a detail two files away. Discourse's service framework fails a step by raising Service::Base::Failure, and the transaction block it raises through is an ordinary ActiveRecord::Base.transaction. Swap the raise for a returned flag and the login code would stay spent on every rejected username.

The consumption and the user save sit in one block at app/services/email_login_code/redeem.rb:51-56, so either both happen or neither does.
api.rubyonrails.org
In practice 
Post.transaction do
  Post.create!(title: "a")
  false            # commits
end

Post.transaction do
  Post.create!(title: "b")
  raise ActiveRecord::Rollback
end                # nothing written

ActiveRecord::Rollback is the one exception the block swallows rather than re-raises, which is why it is the idiom for a deliberate undo.

Understanding Ruby on Rails ActiveRecord::Validations
Validations are per-instance, and only the bang form raises

A model's validations are not a fixed gate every write passes through identically. Each one can be conditional, and a custom validation method is ordinary Ruby that may consult an attr_accessor set by whoever built the record. Two call sites saving the same class can therefore get different checks, with nothing in the model declaration saying so.

How a failure travels differs too. save returns false and leaves the reasons in errors; save! and create! raise ActiveRecord::RecordInvalid carrying the record. A caller that relies on the model as its backstop has to know which form it is calling and, if the check is conditional, whether the flag it hangs on is set.

The reserved-name check is conditional at app/models/user.rb:2160-2166, and the invite path never assigns the flag it reads.
api.rubyonrails.org
In practice

  validate :check, if: :strict
end

Post.new(title: "").save   # => false
Post.new(title: "").save!  # raises
                           # RecordInvalid

Checkpoint E

What happens to a chosen avatar when the two upload-permission checks disagree?

The avatar is now picked before the account exists, so the controller has to predict whether the future user may upload one: it synthesises a group list from the default trust level, the logged-in pseudo-group and the invite's groups, and intersects that with the setting. After creation the response recomputes the same permission the ordinary way, and the client honours that second answer. Where they disagree the picked file is dropped inside a bare catch — deliberately, so a failed avatar cannot fail a created account, but silently. from unchanged code

Understanding Ruby on Rails after_create
after_create runs inside the save's own transaction

Rails wraps every save in a transaction and runs the after_create callbacks inside it, before the commit. Rows those callbacks insert are therefore visible to anything that queries after the save returns — which is how a record can arrive already carrying associations nobody at the call site wrote.

That is what decides this judgment. Joining the trust-level group is an after_create callback on User, so by the time the response is built the new account really is in the group the controller guessed at, and the two computations agree for the default setting. The guess and the reality are still separate expressions, and only one of them knows about a group the inviter lacked permission to add.

The callback is declared at app/models/user.rb:187, which is why the post-creation check can trust a group query.
api.rubyonrails.org
In practice 
class Post < ApplicationRecord
  after_create :tag_it
  def tag_it
    tags.create!(name: "new")
  end
end

Post.create!.tags.count  # => 1

An exception raised in the callback rolls the parent row back too, since it is all one transaction.
