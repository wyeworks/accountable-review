Self-deletion now asks for the username as well as the password

The confirmation challenge on /settings/delete changes from one credential to two: the account's username is now required from every user, and the password is required in addition wherever one is stored.

What changed

One credential became two, for everyone who has two

Deleting your own account was confirmed by whichever single credential the installation held for you: your password, or — when Mastodon stores none — your username. It is now confirmed by the username always, plus the password wherever one exists. The rewritten guard checks the username first and returns early when it does not match; the password check that follows is short-circuited by encrypted_password.blank?, so accounts with no stored password face the same username-only challenge as before and no population loses a factor. The view was reordered to match: the username field is rendered unconditionally and the password field only when there is a password. The description gives the motivation — people reusing one password across accounts, handed from a mobile app into a browser signed in as someone else, were deleting the wrong account.

Before
One field. The password, or the username for accounts Mastodon stores no password for.
After
The username always, and the password as well wherever the account has one.
Attention

What needs your attention

Four judgments, all of them about the half of the challenge that is new to most users: what string counts as a match, what the browser will send, what the user is told when it fails, and where the comparison lives. They are in the order to think about them.

Checkpoint A

Is byte-for-byte equality the right bar for the typed username?

The comparison is Ruby's String#==, so the typed value has to match the stored one exactly. That comparison is not new — the old passwordless branch used it too — but it was previously reached only by users on installations that store no password, and it is now on the path every user takes. Mastodon normalizes a username in two places and the challenge uses neither: Account squishes whitespace out of the stored value on save, and every lookup in the application goes through a scope that lowercases both sides from unchanged code. So an account registered as Gargron is not confirmed by gargron, nor by @Gargron as the profile page spells it, nor by a value carrying a trailing space from a copy-paste. Decide whether that strictness is the intended bar or an accident of where the comparison came from.

Checkpoint B

Does the field now shown to everyone need the attributes the handle inputs beside it carry?

The moved input declares autocomplete: 'off' and nothing else, so an iOS keyboard will capitalize its first letter and autocorrect is free to substitute a word — against a comparison that accepts neither (Checkpoint A). This codebase knows the attributes: the account-migration views pass autocapitalize: 'none', autocorrect: 'off' on the field where you type a handle. The self-confirmation username field in those same views does not, and that has been tolerable because it is behind - else and only passwordless users ever see it from unchanged code. This change takes the same unattributed input out from behind that branch and puts it in front of every user, on the flow the description says mobile users reach through a handed-off browser. Decide whether the raised exposure changes the answer.

Checkpoint C

After a failed attempt, can the user tell what to change?

The failure branch is unchanged and says The information you entered was not correct for any cause. With one field that was unambiguous; with two it no longer names which half failed, and because the branch redirects rather than re-rendering, the show action builds a fresh Form::DeleteConfirmation and both inputs come back empty from unchanged code. A user who mistyped their username retypes their password too, with nothing to tell them the password was never the problem. The session is already authenticated, so there is no third party the ambiguity protects the information from — which makes this a decision about whether the vagueness is wanted here, not a disclosure question. The consequence is drawn as Impact path A.

Checkpoint D

Should the challenge live on Form::DeleteConfirmation rather than in the controller?

The PR grew the challenge in the controller, where it already was. Form::DeleteConfirmation stayed two bare accessors. Its closest sibling is Form::Redirect, the account-migration challenge in the same settings area, which answers the same question — prove you own this account — on the form object: it declares the typed username as an attribute, normalizes it, and adds the error to the field that failed rather than returning one boolean from unchanged code. That shape is what Checkpoints A and C are each asking about from a different side. Decide whether keeping the two challenges different is deliberate, or whether the second one should have moved when it gained a second field.
