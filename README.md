# rails-review-guide

A [Claude Code](https://claude.com/claude-code) skill that turns a Rails pull request into a
published HTML walkthrough — organized by framework layer, so a reviewer can *understand* the change
before judging it.

Schema as a diagram. Endpoints as a contract, with side effects spelled out. Service classes grouped
by what they are authoritative for. And the decisions worth a human's attention, mined from the
code's own comments and commit messages.

## Why

A `git diff` shows you what changed. It cannot tell you what the change *is* — which files carry the
design and which are churn, what order to read them in, which constant is load-bearing, or why the
author put a transaction there.

That gap is [comprehension debt](https://addyosmani.com/blog/comprehension-debt/): the widening
distance between code that gets produced and code anyone actually understands. Generating nine
thousand lines is now cheap; understanding them is not. A PR approved without being understood was
waved through, and the debt comes due the first time someone has to change it.

This skill exists to close that gap for Rails changes specifically, by knowing what Rails reviewers
look for and rendering it as something you can read.

## Install

Copy the skill into a project:

```bash
cp -R skills/rails-review-guide /path/to/your-project/.claude/skills/
```

Or symlink it, so updates here reach every project:

```bash
ln -s "$PWD/skills/rails-review-guide" /path/to/your-project/.claude/skills/rails-review-guide
```

For every project at once, install into `~/.claude/skills/` instead.

## Use

```
/rails-review-guide              # current branch against its base
/rails-review-guide 412          # a PR number
/rails-review-guide https://github.com/org/repo/pull/412
/rails-review-guide feature/some-branch
```

You get back a URL. The page is a private Claude Artifact until you share it.

Re-running for the same PR republishes to the same URL, so the guide tracks the PR across pushes
instead of scattering links.

## What it produces

- **Masthead** — what the PR does in plain language, derived from the code rather than copied from a
  possibly-stale description, plus the metrics that change how you review (production vs test vs
  generated lines).
- **Where to start** — the two to five things most needing human judgment, each verified against the
  source, plus a reading order and a note on which files carry the design.
- **Layer sections** — data and persistence, interface, domain logic, boundaries and configuration,
  tests, and a shallow paired-frontend section. Each appears only if the diff touches it.
- **Coverage ledger** — every changed file and where the guide covers it.

### It adapts to the PR

Sections appear only when the diff earns them, and depth scales with size: one or two changed files
in a layer gets a paragraph, nine or more gets a diagram and a grouping. A four-file bugfix produces
a one-screen guide, not an empty template. If a PR genuinely does not need a guide, the skill says
so instead of generating ceremony.

### It covers the whole diff

Ranking attention is not the same as skipping things. Every file in the diff appears somewhere, even
if only as a ledger row reading "generated by the migration". A reviewer who wants to read all of it
can, and never has to wonder whether something was quietly dropped.

### It is not a code reviewer

Claude Code ships `/code-review`, and many teams add their own. This skill answers a different
question — *what is this, and where do I look?* — and produces a document that outlives the review
rather than comments that vanish into it. Flags are a section within the explanation, not the point.
The skill never posts to GitHub.

## What it assumes

Only that it is running in Claude Code, against a git repository containing a Rails application.

Everything else is discovered: where the Rails root is (repo root, a subdirectory, an engine), RSpec
or Minitest, API-only or server-rendered, the authorization library, and whether the project
documents its own conventions. Where a project has no convention docs, the skill infers house style
from adjacent unchanged code — usually more accurate than a stale document anyway.

`gh` is used when present, for PR metadata and deep links. Without it, or without a PR, the skill
falls back to the local branch and still links citations as long as the commit is pushed. On an
unpushed branch it degrades to plain text rather than emitting permalinks that would 404, and says
so in the page.

## Layout

```
skills/rails-review-guide/
├── SKILL.md                       the procedure Claude follows
└── references/
    ├── guide-outline.md           sections, triggers, depth rules, deep-link forms
    ├── rails-lenses.md            what to look for per layer
    └── page-template.html         design system and component vocabulary
```
